# AI log

How AI was used to build **audit-agent**, written for the Mycrobo AntiSlop hackathon (track `ai-triage`).

## Tools

| Tool | Used for |
|---|---|
| **Claude Code** (desktop app, model Claude Opus 5.5) | Planning, writing all code/tests/docs, running tests and the CLI, debugging, git + GitHub publishing |
| **Claude API** (`claude-opus-5-5`) | Runtime feature: the optional `--llm` triage pass inside the tool itself (`src/audit_agent/llm.py`) |

No other AI tools were used.

## Division of work

- **Me (human):** chose the project, wrote the spec below, directed the follow-ups (publishing, running it, submitting), and handled the hackathon submission.
- **AI (Claude Code):** designed the architecture and wrote the code, tests, fixture repo, CI workflow and README. It ran every command shown here and fixed the bugs those runs exposed.

## The original prompt (verbatim, abridged formatting)

> Build a hackathon project: a simple, architecture-agnostic code-audit agent in Python. It scans any repo (any language, no assumptions about framework or layout) and reports: 1. Security issues … 2. Slop … 3. Coding gaps and loose ends …
> Requirements: CLI `agent scan <path>` with --format (text|json|markdown|sarif) and --fail-on severity; pluggable rule engine; language-agnostic regex/file-level rules plus Python AST rules; optional LLM pass (Anthropic API via env var; fully skipped if no key) that triages findings, removes false positives, and writes a prioritized summary; clean architecture, type hints, unit tests (pytest), a GitHub Actions workflow, a README with architecture diagram, usage, and design tradeoffs, and a sample report generated by scanning an intentionally messy fixture repo. Keep it simple and readable; reviewers grade the repo.

Follow-up prompts: "upload it to my GitHub, public", "what is the project and run it", "I need to submit here", and, after the arena rejected the first `arena.json`, "Add the triage API".

## Timeline

| Step | What the AI did | What went wrong / was corrected |
|---|---|---|
| 1. Design | Picked a zero-dependency core: three rule shapes (`RegexRule`, `FileRule`, `RepoRule`), a deterministic engine, and the LLM as an optional post-processor that can only dismiss or annotate findings. | — |
| 2. Core + rules | Wrote `models`, `workspace` (file walker), `engine` and 28 rule ids across `security.py`, `slop.py` and `gaps.py`. | Severity was first a `str` enum with custom `<`/`>=`, which mixed string and rank comparisons. Simplified to an explicit `.rank`. |
| 3. LLM triage | Wrote `llm.py` with structured JSON-schema output and server-side refusal fallbacks. Critical findings can never be dismissed (prompt-injection guard). Any error falls back to the raw scan. | — |
| 4. Fixture | Built `tests/fixtures/messy_repo` (Python + JS + Go) with planted issues. | Replaced a Stripe-shaped fake key with a generic one, so GitHub push protection would not block the repo. |
| 5. First real scan | Ran `agent scan` on the fixture. | **SQL injection was missed** (the regex broke on `'` inside `"..."`; fixed with a quote backreference). **JS `exec('…' + x)` was missed** (added a pattern). **"TODO: implement" was not flagged as a stub.** **The dedupe key collapsed the three "missing README/.gitignore/LICENSE" findings into one** (the message was added to the key). |
| 6. Self-scan (dogfooding) | Ran the tool on its own repo. | It flagged its own regex definitions and docstrings: the classic linter self-match. Fixed by restricting TODO detection to comments, replacing a SHA-1 fingerprint with plain dict keys, and adding `# audit: ignore[...]` on rule-definition lines. |
| 7. Tests | Wrote 85 pytest tests, including a fake Anthropic client, so LLM tests need no network or key. | 1 failure: JS `exec(` was reported as both code-eval and shell injection. SEC003 was narrowed to `eval` outside Python. |
| 8. Suppression design | Added file-level `# audit: ignore-file[...]` so the rule tests (which must contain bad patterns) don't hide from the scanner wholesale. Also added `skip_docs` so README examples don't trigger code-pattern rules, while secret rules still scan docs. | — |
| 9. Publish | Created the public repo `gkarthik04/audit-agent` with `gh` and pushed. | **The first CI run failed** on the self-audit job. `pip install -e` creates `*.egg-info/PKG-INFO` (a README copy), and the job scanned its own fresh SARIF report. Fixed in the tool: it now skips `*.egg-info`, and `.auditignore` skips `audit-report.*`. Also bumped the Actions to Node 24 versions. The second CI run passed. |
| 10. First submission attempt | Wrote a descriptive `arena.json` (name, track, description…). | **The arena rejected it with `invalid_arena_json`** (the preview step, so no slot was used). The AI had guessed the format. It then found the organizer's public pipeline-test repo (`tirthmoxb/arena-smoke-test`), which showed that `arena.json` is a run contract (`language`, `install`, `test`, `start`, `port`) and that the `ai-triage` track is graded against an HTTP API: `GET /health`, `POST /classify` → `category`, `urgency`, `confidence`. Only that repo's public README, contract and sample tests were read; no hidden tests exist in it. |
| 11. Pivot: triage API | I chose to add the triage API to this repo, keeping the audit agent. The AI wrote `src/triage/` (a deterministic weighted-keyword classifier, a stdlib HTTP server, and optional Claude classification with a rules fallback) plus `app.py`, which runs with no install step. | — |
| 12. Hardening and tests | Added 45 tests: classifier cases, contract shape, and a real-socket server test for every error status. | **The first server test run found a real bug:** for an oversized body the server sent 413 and closed without reading the body. The OS then reset the connection, so clients saw "connection aborted" instead of the 413. Fixed by draining bodies up to 1 MiB before replying. Also dropped `Content-Type` enforcement, because `curl -d` sends form-encoding and the JSON body is validated anyway. |
| 13. First grade: 23.5/100 | I submitted, and the arena graded it: hidden tests 7/30, own tests 0/10, readiness 12.6/20, docs 5/5. The Arena Guide didn't know the `/classify` contract. | The AI diagnosed three grader findings and fixed them. **Own tests 0/10:** the grader's `-q` plus our config's `-q` suppressed pytest's "130 passed" summary line. **#108:** `pytest>=8` wasn't pinned, so the full dependency tree is now pinned with platform markers. **#67:** gitleaks flagged the *fake* credentials that the audit agent's secret-detection tests need. A `.gitleaks.toml` allowlists only those test-data paths. Real code gets no exemption, and nothing real was ever committed. |
| 14. Classifier accuracy | Built three hand-labelled ticket sets (99 dev, 50 holdout, 40 test) and measured before changing anything. Then rebuilt the classifier as a pipeline: defang injected instructions, negation scope, typo tolerance, Hinglish/Devanagari, a "something is broken" fallback, and de-escalation cues. | **The AI's first "100%" was overfitting:** that was the dev set it tuned on. On the holdout the honest number was 66%. After one round of error analysis, a third set was written and scored once: **70% fully correct, up from 62% for the original rules.** That is the number reported in the README. Error analysis also exposed real bugs: "scheduled **jobs**" triggered the *hiring* signal, and "bill**s**" / "pay**ing**" didn't match. |
| 15. Full review before the 2nd submission | I asked for an end-to-end check of everything. The AI re-audited each grader finding and the API against the organizer's reference app. | **The AI found its own previous fixes were fragile.** (a) The `.gitleaks.toml` allowlist only works if the grader honours repo config, and "full history" would still contain the old values. The fake credentials were therefore replaced with values that are unmistakably fake, such as an AWS-style id using digits real AWS ids never contain. Our detector still flags them and generic scanners don't. The allowlist was removed, and git history was squashed so the old values are gone. (b) Requirement pins used platform markers, which a strict "fully pinned" check may reject, so every line is now plain `name==version`. (c) The API rejected text over 10,000 characters, while the reference app accepts any body up to 16 KB; it now accepts and truncates, and uses the reference's `body_size` error code. (d) Fuzzy matching double-counted repeated words and took ~0.5 s on 16 KB of noise; that's fixed and now about 3× faster. Also added a `GET /` try-it page with a hash-pinned CSP for judges and the demo. |

## What was verified, and what wasn't

- ✅ `pytest`: 136 passed locally (85 audit agent + 51 triage API, including accuracy floors and the try-it page's CSP).
- ✅ The grader's own commands from `arena.json` (install → test → start → `curl /health` and `/classify`) were run from a fresh clone.
- ⚠️ The triage categories (`billing` / `technical` / `account` / `general`, urgency `high` / `low`) were taken from the organizer's public pipeline-test repo. The official track brief on the site was empty, so the hidden tests may expect labels this classifier doesn't produce.
- ⚠️ Claude classification mode (`TRIAGE_LLM=1`) is tested only with a fake client, like the audit agent's LLM pass.
- ✅ The self-audit is clean (`agent scan . --fail-on info` → 0 findings).
- ✅ The fixture triggers every rule id (an end-to-end test asserts this).
- ⚠️ **The LLM triage pass has not yet been run against the live Anthropic API.** It is covered by unit tests with a fake client. The repo has no `ANTHROPIC_API_KEY` secret configured.
- ⚠️ The heuristic rules (restating comments, commented-out code, missing tests) are rated `low` because they will have false positives.

## Reflections

- The AI's first drafts of regex rules looked right but failed on real input. Running the tool on the fixture and on itself caught every one of those bugs, so in practice the tests and dogfooding were the review process.
- Making the LLM *optional and subtractive* (it can dismiss, never add) was a deliberate anti-slop decision. The report is always traceable to a deterministic rule.
